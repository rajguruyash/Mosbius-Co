# Integrations, accounts and agent access

Mosbius & Co. is a fan-made project inspired by How I Met Your Mother. It is not affiliated with, endorsed by or connected to the show, its makers or its owners.

This is the reference for **Settings → Integrations & Skills**: what the app can connect your agents to, how each is connected, who can use what, and how much of it has actually been checked. Skills have their own page, [SKILLS.md](SKILLS.md). The security properties and their limits are in [SECURITY_REPORT.md](SECURITY_REPORT.md); the broker's design is in [MCP_BROKER_DESIGN.md](MCP_BROKER_DESIGN.md).

## The rule behind all of it

**Nothing is on, connected, installed or reachable by an agent until a person turns it on, and an agent gets nothing until you give that agent access.** Switching a service on only makes it *available*. Each agent then needs access of its own, set per agent and per tool, and the starting point is no access.

An agent never holds your sign-in, your key or your tokens. It holds a *pass*: a random value that belongs to that one agent and that one integration, that the app can cancel at any moment, and that only works against the app's own loopback address. What the pass may do is decided by the app on every request, not by the agent.

## The flow

1. **Discover.** Pick a service. Each card says how it connects and how far it has been checked.
2. **Connect.** The app tries the ways the service offers, in this order:
   - **Sign in with your account.** The app registers itself with the service for this one sign-in (RFC 7591), opens the service's own page in your browser, and you approve. PKCE protects the exchange and the redirect goes to a random port on `127.0.0.1`. Nothing of the app's own is kept: no secret, no registration beyond the sign-in. Disconnect asks the service to revoke it (RFC 7009).
   - **A sign-in code** (GitHub). A short code you type at the service's page (RFC 8628). It needs an app that you or the project registered at the service; its client ID is a public value.
   - **An app you register.** Gmail, Google Calendar, Google Drive and Slack do not let an app register itself. You register an OAuth app of your own, store its client ID and secret, and sign in once.
   - **A key you create.** A token or API key, stored encrypted by your operating system and never shown again, never given to an agent.
   - **Nothing to connect.** The local servers run on this computer.
3. **Tools are discovered and classified.** The app asks the server what it offers. Each tool is classed **read**, **write** or **destructive** from a list the project pinned. A tool nobody classified is treated as destructive and is never part of *read* or *write*. If you opt in for a server, the app may believe that server's own read-only hint, and only ever to make a tool *stricter*.
4. **You choose which agents may use it.** Per agent, per tool, with an optional end time. A tool that sends, posts or deletes is never included by *read* or *write*; you tick it by name.
5. **The agent uses what it was given.** Everything it does goes through the broker, which checks the pass and the grant on every request and writes the decision to a tamper-evident activity log (names and decisions, never contents or secrets).
6. **You can take it back at once.** Switching a service off, disconnecting it, or taking an agent's access away applies to that agent's next request and cancels the ones in flight. It cannot undo what the service already did.

## What is checked, and what is not

The legend and the two tables below are generated from the data the app itself uses (`src/shared/providers.ts`, `src/shared/agentCompat.ts`, via `tools/lib/catalogue.cjs`), and a test fails if this page and that data disagree. The same data draws the README and the website. The status words in the first column of the providers table follow one rule:

- **VERIFIED**: a real run, recorded in an evidence file in this repository. A stand-in never earns this for a provider. For an *agent CLI* the real thing being checked is the CLI's own behaviour (what it offers, what it calls, what its shell can see), so a run of the real CLI against a stand-in model and a stand-in provider counts; it never counts as a real account.
- **PARTLY VERIFIED**: a real call was made, but not through every route.
- **UNVERIFIED**: built and tested against a stand-in; nobody has signed in to the real service through the app.
- **WIRED, NOT RUN** (agent CLIs): the app writes what the CLI's documentation says it reads; the CLI was not run. No CLI is in this state now: all three have been run.
- **NOT IMPLEMENTED**: not available.

### What the words mean

- **Implemented.** The app has a way to connect an agent to it: code, a catalogue entry or REST template, and a card in Settings. It says nothing about whether it has been run against the real service.
- **Locally tested.** The real server ran on the development Mac and answered a real tool call. It needs no account. macOS only.
- **Stand-in tested.** The way the app connects to it (sign-in, sign-in code, your own app, a key, or the REST route) was run end to end against a stand-in service that behaves like a provider. It proves the app's side of the connection, not the provider's.
- **Real-account verified.** A real sign-in or key was used for a real call, and the evidence file is in the repository. Nothing is in this state yet.
- **Not yet verified.** Implemented, but never run against the real service with a real account.
- **Not implemented.** Not available in the app.
- **✓, partly, —, n/a.** In the tables: yes, only in part, no, and "does not apply" (a local server needs no account, so nothing about an account applies to it).

The Status column uses the app's own status words in capitals: VERIFIED is *Locally tested* (the card in Settings says "Verified"), PARTLY VERIFIED is *Partly tested locally*, UNVERIFIED is *Stand-in tested, not yet verified* (the card says "Not yet tested"), NOT IMPLEMENTED is the card's "Planned", and NOT APPLICABLE is for the AI engine keys, which are not integrations.

### What the agent CLI runs were, exactly

- **Claude Code** was run against the broker with the real CLI and real pinned servers (`evidence/stage-b/stage-b-live.json`), and its project skill folder was shown to be read (`evidence/claude/claude-skills-live.json`). No real provider account was used.
- **Codex CLI 0.142.2** was run for real, in a throwaway home, against the real broker with a stand-in provider behind it and a *stand-in model* in front of it, so the real agent loop ran without any account (`evidence/codex/codex-live.json`, `tools/verify-codex-live.cjs`). It showed: the broker's server starts and is offered to the model with only the granted tools; a tool call made by the model reaches the provider with the provider's own token and never the agent's pass; a tool that was not granted cannot be called and is refused by the broker when called directly; after revocation the open session and any new session are refused; and, with Codex's OS sandbox on (the app's mode), Codex's shell neither has the pass in its environment nor can inspect the process that holds it; with the sandbox off it can (a control in the run). It does **not** show that a real OpenAI model uses the tools well, and it was not run signed in.
- **Gemini CLI 0.68.0** was run for real the same way (`evidence/gemini/gemini-live.json`, `tools/verify-gemini-live.cjs`, 50 of 50 checks, including a section that tries to close F9 and records why it cannot be closed): the exact npm package (`@google/gemini-cli`, installed with install scripts off into a throwaway folder, integrity recorded in the evidence, folder deleted afterwards), a throwaway home, the real broker, a stand-in provider behind it and a stand-in model that speaks the Gemini API in front of it. It showed: the broker's server connects, authenticated by the pass in one variable; the model is offered exactly the granted tool and no other; a call made by the model reaches the provider with the provider's own token and never the pass; a tool that was not granted is not offered, is refused by Gemini if the model asks for it anyway, and is refused by the broker even to a client that holds the pass and asks for it directly; a pass revoked in the middle of a run stops the next call, and the provider is not asked; in a folder you have not trusted in Gemini the integration is disabled (it fails closed); the app's lifecycle hooks are loaded **and run**; and the skills the app installs are found, in the places listed in the table. It does **not** show that a real Gemini model uses the tools well, that a real Gemini login carries over (the app links your login files into each agent's Gemini home; no Gemini login was used), anything on Windows or Linux, or any other Gemini version.

### Four things the Gemini run found

They are fixed or stated, and the run is the reason:

1. **The app's first Gemini design could never have worked on this version.** It wrote the broker's entry and the lifecycle hooks into a *system* settings file. Gemini 0.68.0 skips any system settings file whose folder is not owned by root ("Security Warning: Skipping system settings file ... not owned by root"; the run keeps that as its control), so neither was loaded. Each Gemini agent now gets a Gemini home of its own; its *user* settings are the one layer an app can own. Your own settings are merged in, your login, skills, commands and extensions are linked in, and your own `~/.gemini` is never written to.
2. **The broker turned the real Gemini CLI away as if it were a web page.** Its browser guard refused any request carrying a `Sec-Fetch-Mode` header. Node's built-in `fetch`, which Gemini is built on, adds `Sec-Fetch-Mode: cors` to every request (measured on Node 22 and 26). A real page always sends `Sec-Fetch-Site` with it, and can neither set nor drop it, so the guard now refuses `cors` only when it comes with `Origin`, `Sec-Fetch-Site`, `-Dest` or `-User`, and refuses every other mode. Tests pin both directions, including a client built on Node's own `fetch`.
3. **Gemini loads an integration only in a folder you have trusted in Gemini.** In any other folder it shows the server as disabled and never contacts it. The app does not pass `--skip-trust` and does not write to your trust file: that is your decision, made in Gemini. If an agent's folder is not trusted there, its integrations simply do not appear.
4. **Gemini's shell can read the pass, and no Gemini setting can stop that (finding F9, left open on purpose).** Closing it was attempted on request and measured on the real CLI, with a control of the original exposure (`evidence/gemini/gemini-live.json`, section `f9`). Three limits stand in the way:
   - **The pass has to be in Gemini's own environment.** Gemini expands `$VAR` in its settings from its process environment at start-up, so a command in its shell can read the pass from the processes above it (`ps eww` on macOS; `/proc/<pid>/environ` on Linux, reasoned and not run). This held in every configuration tried, including the two below.
   - **There is no per-variable lever.** Gemini returns the whole environment unless its global redaction is on; naming the pass as blocked with redaction off hides nothing.
   - **The global redaction hides things that are not the pass.** It does remove the pass from the shell's environment, but `SSH_AUTH_SOCK`, `*_KEY` and `*_TOKEN` variables are dropped from its allow list, and values shaped like credentials (a URL with a password, a GitHub-token-shaped value) are removed before the allow list is read. Measured: with every name allowed, `SSH_AUTH_SOCK`, `MY_OWN_API_KEY`, `GEMINI_API_KEY` and both credential-shaped values were still hidden.
   Also tried and not shipped: a `BASH_ENV` start-up file that unsets the pass (Gemini does not strip `BASH_ENV`; it hides the pass from `env` and from nothing else, so it would be a misleading fix), and Gemini's own macOS sandbox (it did not start on the app's isolated-home layout, and it would change what the agent may do). What limits a pass that can be read is what it can do: this machine's broker only, this agent only, this integration only, only the tools in the grant (a run builds the request by hand with the very pass and is refused for every tool outside the grant), and gone when the agent ends or access is taken away.

### Three things the Codex run found

They are fixed, and the run is the reason:

1. **The stand-in provider the tests used was not a valid MCP server** (its tools had no `inputSchema`, and it answered `404` to the transport's `GET` and `DELETE`). Claude Code tolerates both; Codex's typed client rejects the first outright and reads the second as "session expired". Real servers do neither, so the stand-in now behaves like one, and a regression test keeps it so.
2. **Codex's own default does not hide the pass from the shell it runs for the model.** Measured on 0.142.2: variables with `TOKEN`, `KEY` or `SECRET` in the name stay in that shell by default, and Codex's *shell snapshot* (on by default) puts the whole environment back into every command even when a policy excludes a variable. For an agent that has an integration, the app now turns the snapshot off and excludes its own variable names, keeping any exclusions you already set. The run includes a control that shows the pass *is* visible without those two settings. The cost: for those agents Codex re-reads your login shell for each command. **A condition found later:** the pass is also in the Codex process's own environment, and a command can read it there with `ps` once Codex's OS sandbox is off (measured with a control); the sandbox the app uses (`-s workspace-write`) refuses that, so "hidden from the shell" holds while the sandbox is on.
3. **The skills folder differs by CLI.** Codex reads `~/.agents/skills` and `<project>/.agents/skills` (and `.codex/skills`), not `.claude/skills`, so the app installs for Codex and Gemini into the shared folder and keeps a separate record for each folder.

## Who can see the pass, and what it can do

| Delivery | Who can read it | What it can do |
| --- | --- | --- |
| Claude Code: a `0600` file in the agent's own folder | the agent's settings forbid it to read that file, and other agents' files; other processes of yours can | call that one integration's tools, within the grant, until revoked |
| Codex: one environment variable, name on the command line | not the agent's shell, **while Codex's OS sandbox is on** (see above; with it off, a command reads the pass from the Codex process); other processes of yours can | the same |
| Gemini CLI: one environment variable named in the agent's own settings file | **Gemini's shell can read the pass, and no Gemini setting can stop that** (F9: measured, with a control; the CLI's own redaction would hide it from `env` but also variables of yours that must stay visible, and the pass stays readable from the Gemini process anyway); other processes of yours can | the same: only the grant, and the broker enforces it even when the pass is used by hand |
| A hired worker's REST pass (`MD_BROKER_TOKEN`) | the worker and everything it starts, **by design**: the worker calls the broker with it | call the REST integrations it was granted, method by method, until revoked; only given when the worker was granted a REST integration |

In every case the pass works only against the broker's loopback address, belongs to one agent and one channel (a pass for MCP is no use on REST), is held by the broker only as a digest, is replaced when the agent is re-granted, and is cancelled when the agent ends, when you take its access away, and when the app quits. It is never in a response, a log line or an activity record.

**The limit.** A pass is a bearer value: anything running as you that can read the agent's file or environment can use it until it is cancelled. The app cannot stop that, and it does not claim to. What it does is bound the damage: loopback only, one agent, one integration, grants checked on every request, a pass that dies with the agent, and the credential itself never in reach.

## Setting up the identities only you can create

Some providers need an app or an account that only you can create. Exact steps, kept current in [STAGE_A_VERIFICATION.md](STAGE_A_VERIFICATION.md) section 4:

- **GitHub** (sign-in by code): register a GitHub App with *Enable Device Flow* ticked and no client secret; the client ID is a public value.
- **Google Calendar, Drive and Gmail:** join the Google Workspace Developer Preview, create a Cloud project and a Desktop OAuth client. Whether a Desktop client works without its secret is the one open question; the stand-in cannot answer it.
- **Slack:** an internal or Marketplace app approved by a workspace admin. Opting an app in to PKCE cannot be undone without Slack support.
