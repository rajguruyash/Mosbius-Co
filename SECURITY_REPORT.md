# Security report: integrations, authentication, agent access and skills

Mosbius & Co. is a fan-made project inspired by How I Met Your Mother. It is not affiliated with, endorsed by or connected to the show, its makers or its owners.

Scope: the in-app broker, the connection layer (sign-ins), the credential stores, per-agent and per-tool access, the three agent CLI integrations, and skills. Reporting a vulnerability: see [SECURITY.md](SECURITY.md). Design: [MCP_BROKER_DESIGN.md](MCP_BROKER_DESIGN.md). Reference: [INTEGRATIONS.md](INTEGRATIONS.md), [SKILLS.md](SKILLS.md).

Labels: **PASS** (tested, test or evidence named), **FIXED** (found, fixed, regression test named), **OPEN** (a risk that remains, stated plainly), **NOT MEASURED**. "Real" means the real program ran; "stand-in" means a test double stood in for a provider or a model. No real provider account was used in any of the runs below, so **no integration with an account-based provider is verified**.

| F1 | Providers that rotate refresh tokens could be broken by two engines sharing one store: one refresh made the other's token "spent", and the grant was declared dead. | **FIXED** | the store is re-read before a grant is declared dead and a newer record is never overwritten; `test/phase4-known-limits.test.cjs` |

## What a pass is, and where it can be read

See the table in [INTEGRATIONS.md](INTEGRATIONS.md#who-can-see-the-pass-and-what-it-can-do). In short: Claude Code's pass is in a file its own settings forbid it to read; Codex's is in one variable that its shell cannot see **while Codex's OS sandbox is on** (F2; with the sandbox off a command reads it from the Codex process); Gemini's is in one variable that **its shell can read, and no Gemini setting can stop that** (F9, measured); a hired worker's REST pass is in its environment **by design**. A pass is held by the broker as a digest only, belongs to one agent and one channel, works only on the loopback address, and is cancelled when the agent ends, when access is taken away, and when the app quits.

## Considered, and not built

- **Binding a pass to the agent's process** (the broker would learn which process opened each loopback connection and refuse one that is not the agent or a descendant of it). It would stop an *unrelated* local process from using a leaked pass, and nothing else: the agent's own shell, and everything it starts, would still be allowed. Node cannot read the peer of a TCP connection; it would take a per-connection `lsof` or `/proc` walk on macOS and Linux, is racy, and has no portable form on Windows without a native module. The cost and fragility are out of proportion to what it adds, so the pass stays a bearer value, bounded as described below.
- **An expiry on a pass.** An agent can run for days and holds the pass in a header it cannot refresh, so a fixed lifetime would end working agents mid-task without protecting anything the loopback-only, one-agent, cancel-on-exit design does not already.
- **Hiding the pass from Gemini's shell (F9).** Tried on request and not built, because no option in Gemini 0.68.0 is both safe and effective: the global redaction hides variables that are not the pass (`SSH_AUTH_SOCK` included, whatever the allow list says); a `BASH_ENV` start-up file hides the pass from `env` only; and nothing at the environment level stops a command from reading the Gemini process's own environment, where the pass has to be. A Gemini sandbox profile that refuses process inspection (as Codex's does) is the one route that might, on macOS only; it did not start on the app's isolated-home layout, and it would change what the agent may do, so it needs your decision before any work. A partial switch that only hides the pass from `env` could be built and labelled as partial; it would not close F9.
- **Hiding a hired worker's REST pass from its own shell.** The worker calls the broker with it, so hiding it would break the feature. The route judges every request instead, and the default grant is none.

## What remains

- **OPEN. A pass is a bearer value.** Anything running as you that can read an agent's file or environment can use it until it is cancelled. The app bounds the damage (loopback only, one agent, one integration, checked on every request, never the credential). It cannot remove the risk.
- **OPEN. A hired worker's REST pass is in its environment by design**, so every process the worker starts can use it. It exists only when the worker was granted a REST integration; the default is none.
- **OPEN. The legacy `mcp-remote` bridge** (Gmail, Calendar, Drive, Slack on the default engine) leaves tokens in readable files while an agent that uses them runs. It is kept on purpose and removed only on your word; the in-app engine does not do this.
- **OPEN. Gemini's shell can read its agent's pass, and no Gemini setting can stop it** (F9; the three reasons are in the finding). It is the one CLI where it can by default; Codex's shell can too once its OS sandbox is off (F2).
- **OPEN. Gemini loads an integration only in a folder the person has trusted in Gemini**, and the app neither passes `--skip-trust` nor writes the trust file. An agent in an untrusted folder simply has no integrations (measured: the server shows as disabled and is never contacted). That is the person's decision to make, in Gemini.
- **NOT MEASURED. A real Gemini model** choosing tools, **a real Gemini login** carried into an agent's home through the links the app makes (structure checked only), and **Gemini CLI versions other than 0.68.0**.
- **NOT MEASURED. Windows and Linux** for everything above.
- **NOT DONE. No real provider sign-in.** Nothing here shows that Notion, Linear, Atlassian, Sentry, Stripe, GitHub, Google or Slack accepts the app's sign-in. That needs your account and is the largest remaining gap.
- **Builds are unsigned.** Signing and notarising need your Apple Developer ID; without them macOS asks for Keychain access on first use (F6).
